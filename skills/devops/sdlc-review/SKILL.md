# SDLC Review Skill

Independently verify work handed from a Kanban implementation run to the review lane, then approve it, request changes, or escalate. This skill reviews the deliverable and its evidence; it does not take over the implementer's work.

## When to Use

Use this skill when all of the following are true:

- the dispatcher spawned you for a task claimed from the `review` lane;
- an implementer submitted a `review_requested` handoff;
- the task needs an independent verdict before it can be completed.

Do not use it for a separate downstream review card. A downstream card is ordinary implementation work with a review-oriented specification and completes through its own lifecycle.

## Prerequisites

- A Kanban worker context with the current task and run identifiers.
- Native Kanban tools: `kanban_show`, `kanban_comment`, `kanban_complete`, `kanban_request_changes`, and `kanban_block`.
- Workspace access through `read_file`, `search_files`, and `terminal` when the deliverable is code.
- The task's original specification, acceptance criteria, handoff summary, and prior run history must be available through `kanban_show`.

## How to Run

This skill is loaded automatically by the review dispatcher. Start with `kanban_show` before inspecting files or choosing a verdict.

1. Read the task specification and the latest `review_requested` handoff.
2. Inspect the actual deliverable and run relevant verification.
3. Choose exactly one verdict: approve, request changes, or escalate.
4. Record concrete evidence in the terminal Kanban transition.

## Quick Reference

| Verdict | When | Final action |
|---|---|---|
| Approve | Acceptance criteria and verification pass | `kanban_complete` |
| Request changes | Correctable implementation defects remain | `kanban_comment`, then `kanban_request_changes` |
| Escalate | A human decision or external prerequisite is required | `kanban_block` |

A requested-changes transition returns the task to its original implementer. When that implementer requests review again without naming a reviewer, the persisted reviewer provenance routes the re-review back to the same reviewer profile.

## Review Lenses

Vary how you look at the work on each round instead of repeating the same inspection. Decorrelated lenses catch different defect classes: a cold read of the artifact surfaces design and correctness problems that the implementer's narrative would have framed away, execution surfaces claims that do not reproduce, and a strict contract audit surfaces quiet scope drift. Repeating the round-1 lens on round 3 mostly re-finds what round 1 already found.

Determine the current round from the history the task record already gives you: count the `changes_requested` entries in the "Prior attempts on this task" section of your worker context (also visible as prior runs in `kanban_show`). The current review round is that count plus one. Round 1 therefore shows zero `changes_requested` attempts; round 2 shows one; and so on.

| Round | Lens | How to apply it |
|---|---|---|
| 1 | Artifact | Read the diff or deliverable cold, before the implementer's summary. Form an independent judgment, then compare it against the handoff narrative and investigate every mismatch. |
| 2 | Execution | Check out the work and actually run it via `terminal`: build, test, and exercise the reported behavior yourself. Verify each handoff claim empirically instead of re-reading the artifact. |
| 3+ | Contract | Re-read the ORIGINAL task body and acceptance criteria, then audit the deliverable strictly against them. Also verify that every item from every prior `kanban_request_changes` round actually landed. |

The baseline duties in the Procedure section still apply on every round; the lens sets which inspection you lead with and weight most heavily.

### Lens variation for ad-hoc review fan-outs

The same principle applies outside the Kanban review lane. When spawning multiple parallel reviewers via `delegate_task`, give each reviewer a different lens — one diff-only brief, one full-context brief, one checkout-and-run brief — rather than identical briefs. Identical briefs produce correlated verdicts and duplicate findings; varied briefs cover more defect classes for the same review spend.

## Delivery of your findings (read before requesting changes)

Your `reason` reaches the implementer through two bounded channels — both ride
the SAME payload the worker reads (`kanban_show` returns `worker_context` inside
it), so what makes them safe is their POSITION at the head, not a second
transport:

- **At the top of the next implementer run's context.** `request_changes` stamps
  the verdict with its round number and the reviewer records it in the card's
  event payload. The next worker's `worker_context` renders it as
  `## Requested changes (latest review verdict)`, immediately after the header,
  and `kanban_show` returns the same text under the `review_directive` key as the
  FIRST field of its JSON.
- **A durable receipt on disk.** Each verdict is also written to
  `<root>/kanban/review_receipts/<task-id>/round-<N>.md`. The path is in the
  `changes_requested` payload and in the directive block.

Both are bounded on purpose. A card's comment thread can be tens of kilobytes,
and once the `kanban_show` payload passes the tool-result spillover threshold the
agent replaces it with a file pointer whose inline preview covers only the first
~1.5 KB — so a finding that lives only in a comment is exactly what stops
arriving. Put the actionable requirement in the `reason`; keep supporting
evidence in the comment. If your verdict is longer than the direct channel
carries, the worker is told to read the receipt, which holds it untruncated.

`kanban_show` also reports `review_convergence`. When consecutive rework rounds
declare no new revision, `request_changes` escalates to the human lane instead of
returning the card to the implementer: you get a `review_not_converging` event
and the card lands in `blocked` with a `needs_input` label, so a further
`request_changes` is neither needed nor possible. That is the loop's own escape
hatch — use it rather than issuing another round against a deliverable that has
not moved.

"Declares no new revision" means the implementer's handoff carries none of
`commit` / `commits` / `sha` / `head` / `merge_commit` / `published_pr` / `merged`
in a value that names something — a str sha, a list of shas, a truthy bool, a
non-zero number, or a per-artifact mapping such as
`commits: {fix: <sha>, doc_note: <sha>}`. An empty `{}` / `[]` / `""` / `False` /
`0` correctly reads as no revision. Before treating an escalation as real,
confirm the implementer's handoff did not commit under a shape you did not expect,
and check `hermes kanban show <id>` for whether HEAD actually moved.

After the human decides, `unblock` resumes the card in the **implementer's own
lane** with your verdict still at the head of its context, plus the operator's
`UNBLOCK: <reason>` comment. It deliberately does not come back to you: you could
only re-issue `request_changes`, which would re-escalate on the same unchanged
deliverable and leave the implementer unrun. If you want a fresh round on a card
that has been unblocked, the implementer has to hand it back to you first.

## Procedure

### 1. Orient from the durable task record

Call `kanban_show` and identify:

- the original task body and acceptance criteria;
- the latest implementation summary and structured metadata;
- changed files, commit identifiers, and test evidence;
- comments and decisions from earlier runs;
- findings from prior review rounds.

Treat the handoff as a claim to verify, not as proof that the work is correct.

### 2. Compare requested behavior with delivered behavior

Map every acceptance criterion to concrete implementation or output evidence. Note omissions, changed semantics, and unrelated scope before deciding whether to run deeper checks.

For code work:

1. Use `read_file` and `search_files` to inspect the changed paths and their callers.
2. Use `terminal` to inspect the diff and run the project's existing focused tests, lint, type checks, or build commands.
3. Exercise the reported failure path and at least one ordinary control path when practical.
4. Check error handling, edge cases, concurrency boundaries, data preservation, security boundaries, and cross-platform behavior relevant to the change.
5. Confirm that tests assert behavior rather than merely snapshotting source text or constants.

For non-code work:

1. Inspect the complete deliverable rather than only its summary.
2. Check correctness, completeness, formatting, and provenance.
3. Validate referenced URLs or external facts with the appropriate native tools when they affect the verdict.

### 3. Choose one verdict

#### Approve

Approve only when the acceptance criteria are satisfied and the evidence is sufficient. Call:

```text
kanban_complete(
    summary="Reviewed and approved. <what was verified>",
    metadata={"review_outcome": "approved", "reviewer_checks": [...]}
)
```

Include the exact checks that passed and any bounded caveat that does not block acceptance.

#### Request changes

Use this for specific, correctable defects. First record actionable findings:

```text
kanban_comment(
    task_id="<current-task-id>",
    body="Changes requested:\n1. <file or artifact + defect>\n2. <required correction>",
)
```

Then return the same task to its implementer:

```text
kanban_request_changes(
    reason="<concise summary of the required corrections>"
)
```

State where the defect is, how it reproduces, why it violates the task, and what minimum outcome would resolve it. The transition does not use blocker recurrence accounting.

#### Escalate

Use escalation only when the reviewer and implementer cannot resolve the problem without a human decision or external prerequisite:

```text
kanban_block(
    reason="escalation: <decision or prerequisite required>"
)
```

Explain the blocked decision and the smallest information needed to continue.

### 4. Preserve role separation

Do not edit the implementation while acting as reviewer. Request changes and let the implementer produce the next candidate; then independently verify that candidate in the next review run.

## Pitfalls

- **Rubber-stamping:** A passing handoff summary is not independent evidence.
- **After two consecutive no-change resubmissions, stop re-issuing findings and diagnose the transport.** A card whose comment thread outgrows the tool-result spillover threshold has its `kanban_show` payload replaced by a *pointer* to `cache/spillover/call_*.txt` — so the implementer never reads your findings and cannot act on them, no matter how precise they are. Symptom: `changed_files` named in the handoff that are byte-identical to the previous round's commit (check `md5sum <file>` against `git show HEAD:<file>`, and compare mtimes against the prior commit time — a mtime *earlier* than the commit it supposedly produced is conclusive). Confirm the mechanism by counting write-tool calls per implementer session in the implementer profile's `agent.log`; sessions that made `0` `write_file`/`patch` calls while `kanban_show` spilled are the smoking gun (`grep cache/spillover agent.log` shows only persist lines, never a read). A `request_changes` cannot converge in that state — escalate with `kanban_block(kind="needs_input")` AND create a fresh card carrying the fix packet **inline in its body** (fresh bodies are delivered intact). Repeating the findings is the anti-pattern: each round grows the thread and pushes more of it out of reach.
- **Comparing pytest failure SETS across two trees: normalise the truncated suffixes first.** `pytest -q` writes `FAILED test_x.py::node - AssertionError: ...` with a **length-dependent** truncation, so identical failures can string-differ between runs and `comm` reports them unequal. Strip the ` - <detail>` suffix (`sed 's/ - .*//'`) before sorting/diffing, or compare the node ids alone. Read the *comm output*, not your own eyeball on concatenated terminals — one mis-read here manufactures a phantom finding.
- **A non-blocking fix reported as applied can be absent because the commit ADDED the block rather than editing it — anchor the diff at the commit's own parent before faulting anyone.** A rework round that fixes blockers and separately claims cosmetic fixes (a corrected sentence, reflowed blank lines) in a shared append-only file can land the blockers in a fresh commit while the cosmetic text survives untouched, because the previous round's edits were never committed and the new commit re-adds the whole entry from the stale committed base. Symptom: the sentence still misstates the diff and the blank-line count is unchanged, while every blocking finding is genuinely resolved. Diagnose with `git show --stat <sha>` + `git diff <sha>^..<sha>` on the artifact: if the heading is an ADD (`+## …`) rather than a context line, the commit could not have carried the correction, and an unreachable-blob sweep (`git fsck --unreachable` filtered for a blob containing the card id) confirms the corrected variant never existed on any ref. Verdict rule: do not re-block a multi-round card for a stale cosmetic sentence with no factual content — record it with its attribution (inherited from an uncommitted round, superseded by the committed state) and approve, since re-issuing it would cost another full round for zero change in the deliverable's truth. Attribute the *mechanism* separately from the author: the implementer's handoff restated its own previous round's sentence, so say that plainly instead of implying the current run fabricated it.
- **A verification report's findings can be a snapshot of a mid-flight WORKING-TREE revision — compare the artifact's commit/mtime against the reporting run's window before calling a finding phantom, and reconcile the tool's count against your own before disputing it.** A report card whose run spans it (measured: run 02:28–03:25, artifact written 02:50:27 and committed 02:50:59) will legitimately record findings that exist on NO committed revision — here a HIGH `broken_link` whose line was a wikilink in the uncommitted wiki-keeper draft and literal bold text by commit time, so `git show <sha> -- <artifact>` shows no link and the validator reports 0 broken links board-wide. Confirm with `git log -1 --format='%h %ci %s' -- <path>` and the file mtime against the run's `started_at`/`ended_at` from `task_runs`, then state it as a **snapshot artifact of the draft, not fabrication** — the implementer measured what was on disk. Re-issue only if an acceptance criterion depends on it; here the AC (`page renders + documented layout`) held, so it was recorded non-blocking. Corollary: reconcile the tool's own counting semantics before disputing its number — `wiki-validate.py` computes `lines = body.count("\n") + 1` (CONTENT lines, frontmatter excluded), so it reports 261 for a 278-line file; the `wc -l` "mismatch" is two counting conventions, not an error, and the same tool will prove `page_too_large` is NEW (parent revision 175 total lines ⇒ content ≤175 < 200 limit) when the report labels it "pre-existing".
- **Do not treat a full-suite total that differs by one as a regression finding.** Handoffs and reviewers run the same suite on the same host minutes apart and can legitimately land on `11 failed/399 passed` vs `10 failed/400 passed`. Re-run the named suspect **standalone** (a flaky wall-clock-budget test passes 2/3) and if it explains the delta, report the *invariant* (identical failure sets, +N new passes) instead of the absolute counts — those are host-flake-sensitive and must not be quoted as evidence.
- **Never trust an attachment's reported `size` — read the file.** A row can carry a stale size (e.g. `400` for an 18 KB file) whenever the upload's `content_base64` was hand-authored rather than generated from the bytes; the on-disk `stored_path` is still complete. Verify with `gzip -t`, a member count, and an md5 against the workspace copy. Re-attaching identical content produces a *second* row, not an update — check for byte-identical duplicates before reporting a discrepancy.
- **Column-existence vs column-value assertions:** when a handoff adds schema + a backfill/migration, a test asserting `col in PRAGMA table_info(...)` proves the DDL ran, not that the column is populated. Reproduce the backfill yourself and read the values: a column can be added, its sibling populated, and itself hardcoded `None` on one of the two write paths (forward vs backfill) while the existence assertion stays green. Same class: a version/stamp column carrying different strings for the same row shape across the two paths.
- **"N consumers rewired" is a claim about a set, not a count:** grep every reader of the deprecated column and check each one, instead of trusting the named ones. A migration that fixes the consumers the implementer remembered leaves the rest reading corrupt data through a live path (e.g. a governance/promotion gate) — that is a failing acceptance criterion, not a follow-up.
- **A disagreement COUNT is not a finding until you state its tolerance.** When a handoff quotes "N of M rows are wrong", recompute the count across a tolerance sweep before accepting or disputing it. A count at `tol>0` (every row differs by float noise or a rounding step) and a count at `tol>0.05` (materially different) are different claims, and implementers/reviewers trade them across rounds — e.g. "17/18" vs "18/18" both failing to reproduce against a true "18/18 differ, 13/18 materially". Report the tolerance you measured at; a bare count is unreproducible.
- **A residual matching the writer's rounding step is not a provenance error.** Before flagging "the stored value was not computed from the columns it should have been", check the rounding: `round(R, 4)` puts a ~5e-5 residual on every row and looks exactly like "derived from a different pnl". Resolve *which* input reproduces the value row-by-row (compare candidates side by side) instead of concluding from the residual size; the same trap makes a correctly-derived column look hardcoded.
- **A tracer that monkeypatches library call sites cannot validate a "0 reaches" claim — switch mechanism class and drive it with a positive control on real code.** Three consecutive rounds can burn on instrument blind spots when the reviewer and implementer both patch the same library surface: `sqlite3.connect` patched at the Python binding misses URI-form filenames (`file:/abs/path?mode=ro`) unless the resolver unwraps the `file:` prefix and strips `?query`/`#frag` before `Path()`; a `Path.resolve()` on a relative argument also silently classifies as non-live. Reach for a *different* mechanism — `sys.addaudithook` sees the raw C-level arguments to `sqlite3.connect`/`open`/`os.remove`/`os.replace`, so it cannot share the patching assumption — and then prove detection power on **real code, not a synthetic one-liner**: point the tracer at a detached pre-fix worktree *as* the "live" tree and confirm it records the reaches the reviewer previously attributed. A post-fix zero is only evidence if the same instrument, same files, same tree shape recorded non-zero one revision earlier and the trace files carry a per-process load sentinel (so "0 records" is distinguishable from "the tracer never ran"). Add per-pid trace filenames: children `subprocess.run`-spawned inherit parent env, so anything keyed off a run-scoped variable makes the child clobber or silently append to the parent's log — an under-count that reads as clean.
- **A `git push` you did not perform can still invalidate a "never pushed" handoff — check whether a scheduled backup swept the commits.** A card's commits can appear on `origin/master` mid-review because an automated job (e.g. a cron running `git add -A && git commit && git push`) picked them up, so every handoff's "on no remote branch, never pushed" becomes stale through no worker fault. Attribute it before treating it as a constraint violation: `git reflog show --date=format:'%m-%d %H:%M:%S' origin/master` shows `update by push` stamps, and a recurring daily clock time (e.g. every day at `04:30`) identifies a schedule rather than a person. Then confirm the reviewed revision itself is intact with `git diff --stat <reviewed_sha> HEAD -- '<relevant glob>'` — an empty code diff means your verification still holds and only the citation is stale; report the automation as a separate finding and do not fail the deliverable for it.
- **A "no fixture in the suite can…" acceptance criterion is scoped to what the runner collects — verify scope before hunting siblings.** When the criterion says *in the suite*, an orphan standalone script that pytest collects **0** tests from (documented in a plan file, run by hand, absent from every suite log) is outside the criterion even when it performs exactly the damage class the card is about. Demonstrate the scoping (`--collect-only` count, `grep` the suite logs) rather than assuming, then report the out-of-scope instance as a **non-blocking follow-up** with its measured damage — do not request changes on a criterion the artifact is not bound by, and do not quietly omit the finding either.
- **Test assertion strength: column-EXISTENCE vs column-VALUE, and pin the fix.** A test asserting `col in PRAGMA table_info(...)` proves the DDL ran, not that any value landed. When a round-1 finding was "the column is NULL but the value is in the JSON beside it", require a VALUE assertion on *every* write path — then confirm the new assertions are RED at the pre-fix commit (copy the new test file into a detached worktree at the old commit). Green-at-both-revisions assertions pin nothing.
- **An "N live reaches" / "0 records" count is only as good as the tracer's path resolver — prove the instrument SEES the reach form before believing a zero.** A tracer that funnels `sqlite3.connect(db)` through `Path(db)` resolves plain paths but returns "not live" for the URI form `sqlite3.connect(f"file:{db}?mode=ro", uri=True)` — so a suite can keep opening the live DB while the trace reports zero, and the reviewer's independent tracer reports zero too (both share the bug, so agreement is worthless). Symptom: the handoff's post-fix trace is a 0-byte file and the pre-fix count is suspiciously close to the number of *plain*-path call sites. Prove detection power first on a scratch tree — one plain connect, one URI connect, one non-live path that must NOT be logged — then `grep -rn 'uri=True' <repo>` for the call sites the instrument must cover. Two corollaries: (a) a WAL-mode `mode=ro` open still **creates** `-shm`/`-wal` when absent and moves `-shm` mtime when present, while leaving the main DB md5 unchanged — so "read-only" reaches are invisible to an md5-only acceptance check and a metadata-only `-shm` delta is expected, not a defect; (b) a pytest-plugin tracer is blind to `subprocess.run([... python ...])` children, so add `sitecustomize`-based child coverage (pid-suffixed trace files) before claiming a whole-suite zero.
- **Reproduce a threshold/limit claim by ASSERTING the limit was crossed, not by reading the number.** A handoff's repro command can silently omit the flag that reaches the pathological size, so the harness prints a plausible pair of numbers with `delivered == raw` and **no spillover at all** — the `BEFORE` number then never matched the documented one. Before accepting any "raw N chars -> spilled" pair: re-run with the documented flags, confirm the raw length actually exceeds the threshold AND that the payload really spilled (`'<persisted-output>' in delivered`), and only then compare. A repro that did not cross the threshold is not evidence of anything; the same run without the flag can be ~half the size.
- **"that grep undercounts because the file has NUL bytes" can conflate TWO independent mechanisms — measure the SCOPE before attributing a count gap to binary content.** A handoff explaining "the plan's command reports 21, not 84, because `agent.log.1` carries NUL bytes" mixed two causes: the `21` was **scope alone** (`{agent,errors}.log` brace-expands to 2 files, 6+15=21, and that total is *identical* with `-a`), while the binary-mode effect produced a *separate* gap (multi-file plain `grep -h`/`-r` prints `grep: agent.log.1: binary file matches` and yields 76 vs 84 — that one file contributes 2 instead of 10). Per-file `grep -c` equals `grep -ac` for **every** file; the truncation exists only in multi-file context-printing mode. Rule: when a handoff or plan attributes a count difference to file content, re-run the *same* command with `-a` at the *same* scope — if the number does not move, the cause is scope (a brace/glob that expands to fewer files than the author assumed), not bytes. Report the two gaps separately, and check the operative figure the card actually gates on (here 84 lines / 42 executions / 0.526%, all reproduced) rather than the parenthetical mechanism — a mis-attributed explanation with correct numbers is a non-blocking precision finding, not a `request_changes` when no acceptance criterion depends on it. Corollary: a live-log count of a denominator (successful handoffs) drifts between runs (7987 → 7990 here) — quote the *rate* invariant, never the absolute count.
- **A reviewer's own session env breaks harnesses that pin a scratch HERMES_HOME.** A review worker runs with `HERMES_DELEGATED_CHILD_CONTEXT=1` and `HERMES_KANBAN_DB` pinned to the live board, so `kb.init_db()` on a scratch root hits `connect()`'s read-only descendant branch and dies with `sqlite3.OperationalError: unable to open database file` — which looks like a defect in the deliverable but is your environment. Run such harnesses as `env -u HERMES_DELEGATED_CHILD_CONTEXT -u HERMES_KANBAN_DB PYTHONPATH=<tree> python3 <harness.py>`; to measure the pre-fix side, point `PYTHONPATH` at a detached worktree of the baseline commit (the harnesses are usually already written to feature-detect the fix and fall back).
  Corollary: a `grep`/pipe pattern that literally contains a guarded command string (e.g. `hermes update`) is refused by the command guard even when it is only filtering output — filter on the stable substring instead.
- **A rename that changes an emitted event/column/flag name is a claim-invalidation sweep, not a local edit.** When a round renames what the code emits (e.g. `<stem>_forced_not_owner` → `<stem>_displaced_not_owner`), every comment, docstring, and `--help` string that *names* the old symbol becomes a false claim about behaviour — and those comments are usually the only documentation of the event family, so a downstream wiki/doc card is told to "verify against the source". Sweep `grep -rn '<old_name>'` across source, parser help, and plugins, then drive each named call path in a hermetic harness and assert the **measured** event against the site's own text. Pin it with one test per documented name — a test asserting the emitted name does not stop a later comment from claiming a different one.
- **A page's landing entry in the change ledger restates its claims and is NOT swept by later rework — treat `log.md` as a claim surface, not history.** A wiki landing card writes the page AND an append-only `log.md` entry that paraphrases the page's figures and rules; a subsequent rework round that corrects the page fixes only the page, leaving the ledger carrying the pre-fix sentence. The ledger is usually the vault's *mandated* record ("every action must be appended to `log.md`"), so the stale text is the survivor most likely to be copied forward. Symptom: after a round that fixes a rule's operator/number on the page, `git diff <fix-sha>^..<fix-sha> -- <ledger>` is **empty**, and sweeping the corrected token/vocabulary across the tree returns the page (fixed) plus the ledger (stale). Same shape for `index.md`/hub one-line summaries. Fix by sweeping every surface the landing round wrote, not just the page: `grep -rn '<the corrected predicate or vocabulary>' <tree>` and confirm each hit is internally consistent with its own stated count. Do not revert the page to match the ledger.
- **Before trusting ANY zero or count out of a structured report, pin the field names by sampling one record — a wrong key yields a vacuous zero board-wide, and a raw text grep yields phantom findings instead.** Reviewing a wiki page's validator output produced both errors in sequence. (a) My first filter looked for `file`/`path`/`page` and reported "0 findings on this page" — but also 0 for *every* page, which is the tell: the schema keys on **`target`** (sample one record and read its keys before filtering, as you would before a tracer's zero). (b) With the key fixed, `grep -c '<page-name>' <report>.json` still returned **19** hits — all of them link-graph inventory (`$.pages[N].outbound_links[0]`, `inbound_links[0]`, `.path`, `.slug`), not `findings[]` entries. A raw grep therefore reads as 19 phantom page findings while the page has zero. The durable instrument is a JSON-path walk that prints the *path* of every occurrence, or a parse of `findings[]` with the sampled key — never a substring count against a mixed-structure JSON document. Corollary: assert a non-zero denominator (total findings board-wide) alongside any per-page zero, so "0 for this page" is distinguishable from "the filter matched nothing anywhere".
- **A verification script that reports the claim's success string while having SCANNED NOTHING is the same class as a blind tracer — read its population count before its verdict.** An attached sweep whose git invocation is misspelled (`git lstree` for `git ls-tree`) dies on the file listing, then prints `pages scanned: 0   distinct hex tokens: 0` followed by the exact expected string (`UNMAPPED … tokens: 0`) — a vacuous green that looks like a reproduced claim. Before trusting any zero from a supplied instrument, assert its denominator is non-zero AND correct (184 pages / 469 tokens here, not 0), then apply the one-word fix and re-run to confirm the number is unchanged for a real reason. A mechanical re-point/find-replace edit can also *introduce* a defect on a page the card owns: measured here, a SHA re-point rewrote `| Auto-backup…` as `|| Auto-backup…`, adding an empty first cell that shifted the row right and silently dropped its Result cell in two independent renderers, while the vault bad-row total moved 21→22. The durable instrument is a delta against the pre-card revision over the whole artifact tree, not a per-page eyeball — and see the raw-pipe-counting pitfall above for why a parser-based cell audit returns a false clean.
- **A history rewrite landing AFTER a deliverable's commits invalidates every cited SHA in it — map old→new by `(committer epoch, subject)`, and do not fail the deliverable for it.** Stronger than the `--amend` case above: a `git filter-repo`/BFG run (e.g. stripping oversized blobs) rewrites every commit id while preserving committer timestamps and subjects, so a wiki/doc corpus written and verified hours earlier suddenly cites 26 dead ids across 19 pages. Diagnose by mtime + reflog: `refs/heads/main` mtime and `git reflog --date=format:'%Y-%m-%d %H:%M:%S'` show the rewrite landing at 18:19 while the deliverable's commits stamped 16:17–17:55 — i.e. the SHAs were correct when written. Prove it with `git cat-file -t <sha>` against BOTH the live repo and the pre-rewrite backup, then recover the mapping by exact `(committer epoch, subject)` equality (NOT date proximity — two `auto-backup:` commits can share a day). Two rules: (a) the fix belongs in a NEW card parented to the reviewed one, not in `request_changes` — a deliverable cannot be required to predict an environment change that lands after its last commit; (b) act before the pre-rewrite backup is pruned (`hermes-backup-recovery`'s rewrite section schedules it for deletion), since that backup is the only place the old ids still resolve. Report the affected-page count and the 4-of-5-in-scope figure so the follow-up is sized.
- **The "alive in pristine, dead in live" SHA differential is blind to a token that is dead in BOTH repos — including a simple transposition.** A re-point census built as `pristine_has(token) AND NOT live_has(token)` cannot see a cited id that never resolved anywhere: measured `dcbb6d6d` (a **transposition of `dcb6d6d0`**, the `auto-backup: 2026-09-09 04:01` commit whose post-rewrite id is `fbd5f5c`) sitting on a wiki page while the census reported "26 tokens, all mapped, complete" and did not list that page at all. Close it with a one-repo-independent check over **every** backticked hex token on the page — `git cat-file -t <token>` against the live repo (and the pristine one only to attribute *when* it died) — rather than a two-repo intersection. Attribution rule that decides the verdict: if the garbled token appears verbatim in the parent deliverable/report the page was landed from, it is a **briefing/report defect, not an implementer defect** — still `request_changes` the page (it must not cite an unresolvable id), but say where it came from, and post the detector gap as a comment on the census card so the sweep's method, not just the page, is fixed.
- **An implementer's fixes can be correct on disk and not exist at all: verify COMMIT DURABILITY separately from artifact correctness.** A round that resolves every finding in the working tree and reports "validator passes, git diff shows only the fixes" may have committed nothing — `git show HEAD:<page>` then still carries the pre-fix state (the broken link, the off-by-one pointer, the missing frontmatter key) while the reviewer reads the fixed file on disk and approves. Three checks settle it, all cheap and all agreeing: (a) `git log --all -S'<marker string from the fix>' --oneline` → empty means no ref anywhere contains it; (b) `git rev-list --all --objects | grep <worktree blob sha>` → absent means the file's blob is unreachable from every ref (`git hash-object <path>` gives the worktree blob); (c) `git show HEAD:<path>` for the *pre-fix* text. Cross-check the handoff metadata: a round that omits the `commit`/`commits`/`sha`/`head` key (`_REVIEW_REVISION_KEYS`, and note the value may be a str, list, dict, or numeric — see `_revision_value_declares`) is invisible to the kernel's revision predicate, so `no_revision_streak` climbs while the tree genuinely moved — and conversely a handoff that *does* name a sha only in prose still counts as "no revision". Escalate the durability gap as blocking when the repo's own convention demands commit+push (a wiki/AGENT-ENTRY or equivalent `commit + push` rule, and prior rounds of the SAME card that were committed) — an uncommitted round is then a process regression, not a formality. **On a shared worktree this is a live hazard, not bookkeeping:** check `ps`/`git reflog` for a sibling card writing the same files and `git status --porcelain` before you finish — in one measured review the dirty set grew 2→5 files and a sibling rewrote the shared `log.md` *after* the reviewed edit, so the deliverable survived only by luck. Never "fix" it by reverting another card's uncommitted work.
- **A re-point/migration card's OWN mapping table is a claim to audit, not the universe of affected tokens — sweep the whole token space.** A card that says "re-point the 26 SHAs" and lists 26 rows can be an incomplete briefing: measured here, a 27th id (`18610638`, an `auto-backup: 2026-09-12 04:01` commit) resolved in the pristine backup, was dead in the live repo, and stayed cited 13x across 8 of the same 19 pages the card named — so the AC "0 hits for each old SHA" passed for the 26 listed and failed for the corpus. Detect it with a **completeness sweep**, not by re-checking the table: extract every `[0-9a-f]{7,40}` token from the artifact tree and test each with plain `git cat-file -e <tok>` (plain `-e`, so blobs/trees count too) against BOTH the pristine backup and the live repo. The finding is exactly "resolves in pristine, absent in live, not in the table" — and the fix is a new mapping row, since all the listed rows may be individually correct. Two corollaries: (a) `cat-file -t <tok>^{commit}` silently excludes merge commits — enumerate with `--all` and no `--no-merges`, or a 2-parent merge row looks like a mapping failure; (b) when several commits share a *day* (multiple `auto-backup:` runs), settle a candidate by **parent-chain consistency** — the new sha's parent must be the table's own mapped successor of the old sha's parent — plus an unchanged payload check (`git show <new_sha>:<config>` vs the old), never by date proximity alone. Finally verify occurrence parity (per-page count of old @pre == per-page count of new @HEAD) so a dropped site is distinguishable from a deliberate exemption; an exemption is only legitimate when the residual is a non-git artifact (a `raw/` FILE NAME), which you prove by showing no object of that name exists in either repo.
- **A history rewrite also silently inflates the review-convergence counter — check `_REVIEW_REVISION_KEYS` before trusting an `escalate: true`.** A rework handoff that names its commit only in the summary prose, or stores it under a key the kernel does not read (measured: `metadata.commit_hashes`, and separately `metadata.commit_pushed` — neither is in `kanban_db.py`'s `("commit","commits","head","sha","merge_commit","published_pr","merged")`), counts as "no new revision". Two such rounds make `no_revision_streak` hit the limit and a *further* `request_changes` auto-blocks a card that is demonstrably converging. Reproduce by reading `task_runs.metadata` for the runs with `outcome='review_requested'` and applying the kernel predicate shape-tolerantly; then state it as a non-blocking finding (the mechanism worked — `review_not_converging` fired 0 times) rather than escalating. Rule for implementers: put the commit under `commit`/`commits`/`sha`, not a bespoke key.
- **Any `sha` a sibling card tells a downstream worker to "verify against" can be invalidated by a later `commit --amend`.** A handoff comment written at 19:36 citing the then-tip is stale the moment the implementer amends twice (19:40, 19:41) before finishing. Verify with `git merge-base --is-ancestor <sha> HEAD` (rc=1 ⇒ dangling) and `git reflog --date=format:'%H:%M:%S'` for the amend trail, then compare `git diff --stat <stale_sha> HEAD` — comment-only drift means the cited content is still right but the instruction is unreachable. Report the correct sha and flag it, because this recurring finding means a prior "fix the citation" round did not durably land.
- **For a docs/wiki artifact, verify the content PARSES, not just that it exists and validates.** A landing card's ACs typically say "page created", "validator passes", "not an orphan" — none of which touch legibility, so a markdown defect survives a green validator and a passing review. Render the artifact through a real parser (`markdown_it.MarkdownIt('commonmark').enable('table')`; assert a `table_open` token per table block) rather than eyeballing it, and pin any newly-added table: a round that fixes a table's *numbers* can break the table itself. The concrete trap — a header carrying a **doubled leading pipe** (`|| Lane | a | b ||`, 7 cells) above a **5-column delimiter** leaves header cells ≠ delimiter cells, and GFM then parses the whole block as a paragraph, publishing the correction as a literal wall of pipes. A doubled leading pipe alone is harmless (12 vault lines use it and render), so attribute the failure by **cell-count mismatch**, not by the `||` styling. Prove blame with a vault-wide scan — every table-shaped block (line starting `|` whose next line is a `|-:` set) across every tracked `.md`, reporting the non-renderers: `1 of 292 in exactly one file` is a regression verdict, `many` is a pre-existing style issue — and compare the count against the previous revision to distinguish "introduced this round" from "always been there". Minimal fix to hand back: make the header single-leading-pipe with cells == delimiter columns. **The instrument matters more than the finding: a `markdown_it` token count CANNOT detect this class — the parser NORMALISES every row to the delimiter's column count, so a doubled-pipe row returns N cells with an EMPTY FIRST CELL and the content shifted right.** A parser-based "cell count != delimiter count" audit therefore has a positive control that returns 0 (verified on a synthetic doubled-pipe row: `markdown_it` gave 5/5/5 cells and `bad_rows=0`). Count **raw pipes** instead (strip one leading/trailing `|`, split on `|`) and require the `--positive-control` to return exactly 1 bad row BEFORE believing any zero. Also report the **delta against the pre-card revision**, not the absolute count: raw counting includes pre-existing `||` styles and unescaped-pipe cells, so `26 @HEAD` vs `26 @pre-card` (delta 0, no regression) and a parser-based `23` are both "clean" — only the delta is the verdict.
- **A validator A/B that inherits its tree from the environment rather than CWD is VACUOUSLY zero-delta — pin the tree explicitly before believing any `delta = 0`.** A handoff's "A/B over this tree vs. HEAD shows these edits add 0 findings" can be true and meaningless at once: if the validator resolves its corpus from an env var (measured: `wiki-validate.py:WIKI_PATH = os.environ.get("WIKI_PATH", "~/knowledge/wiki")`) then running it with `cwd=<worktree>` audits the LIVE tree twice, and the stash-based A/B variant is doubly hollow — after the work is committed there is nothing to stash, so it also compares the tree to itself. Both print a confident `delta = 0`. Re-run with the tree pinned per side (`env WIKI_PATH=<worktree>`) and confirm the two runs report different `wiki_root`/root paths in their own output BEFORE reading the delta; only then is the finding set comparison evidence. Corollary: expect a small non-zero delta from *re-statements* of a class that already existed (a page already flagged `page_too_large` grows past the limit again) — that is not a new finding kind and must be reported as such, not as a regression.
- **A wikilink carrying a `#anchor` can be unresolvable BY CONSTRUCTION — settle it with a positive control that names a REAL heading on the target page before accepting a renamed-anchor fix.** When a round answers "repair the dead anchor" by keeping the `#anchor` and correcting its name, that can be a non-fix: a line-based validator that never strips the fragment will flag EVERY anchored link regardless of whether the heading exists. Measured in `wiki-validate.py`: `extract_wikilinks` (l.224) keeps the whole `[[…]]` text and the resolver (l.594) computes `link.replace("/","-").replace(" ","-").lower()` — no `#` handling, no heading lookup — so `[[fork-upstream-sync#method-and-decision-rule]]` is flagged even though `## Method and decision rule` exists on that page. Rule: (a) run the one-line control FIRST — append a plain link and an anchored link to a scratch copy of the tree and confirm the plain form is clean while the anchored form is flagged; (b) census the whole corpus (`grep -rno '\[\[[^]]*#[^]]*\]\]'`) — if the flagged anchors are the only anchor links in the vault, the required fix is to DROP the fragment, not rename it; (c) fix the instruction you hand back so the next round cannot repeat the same misreading. Corollary: a handoff can claim a residual class is gone while one instance survives — re-grep the artifact yourself (`grep -n '\[\[' <page>`) rather than re-reading the claim, since "0 remaining <form> links across both pages" is a claim about a SET, not a count.
- **A frontmatter parse error short-circuits the rest of a line-based validator — a green run can be green because it never reached the check.** When a page's frontmatter uses a form the validator's simple line parser cannot read (observed: a multiline `sources:` / `relations:` sequence, `key:` followed by `  - item` lines — every `- item` line has no colon, so it emits `unparsable line` and the checker `continue`s past required-field, TYPE, relation-vocabulary, confidence and tag validation for that page), the reported finding for the page is only the parse error, and the "passes the validator" acceptance criterion is satisfied vacuously. Detect by comparing the page's frontmatter FORM against its siblings (a one-of-180 outlier is the tell), then run the unmasking A/B at full-corpus fidelity: inline the offending block on a detached worktree copy and change nothing else — the newly appearing findings are the masked set. Report the PER-PAGE finding count, never the board-wide total, since the total cannot distinguish "clean" from "not reached".
- **Before refuting a token-count claim, pin the column semantics — an already-exclusive column minus its sibling yields negative "uncached" values that read as a wild discrepancy.** A local usage table commonly stores `input_tokens` ALREADY net of the cache (`cache_read_tokens` is a separate sibling, not a subset to subtract). Computing `input_tokens - cache_read_tokens` then produces negative uncached counts and a gap percentage in the hundreds, which looks like a catastrophic refutation of a claim that is in fact exact. Symptom: uncached values negative, or a gap far outside the stated tolerance. Rule: reproduce the claim with the author's OWN filter and column choices before disputing it, and state the tolerance you measured at — a count you cannot reproduce is not a finding.
- **A handoff's suite counts can be UNREPRODUCIBLE in a kanban worktree while the invariant it asserts is correct — measure the failure SET, never the numbers.** Tests that resolve paths *outside* the repo (e.g. `REPO_ROOT.parent / ".hermes" / "scripts"`) pass in the main checkout and fail under `<repo>/.worktrees/<task>` or `kanban/workspaces/<task>/wt`, because the parent directory there holds no sibling tree. The implementer, working in that same worktree, can therefore quote a passing count that no reviewer can reproduce. Re-run the A/B yourself against a detached worktree of the declared base, `comm` the normalised failure sets, and report the set identity plus the count delta — then attribute the delta (path-layout test, not the change) instead of failing the deliverable. Corollary: a test that passes only in the main checkout is a *test* defect worth a non-blocking finding, since CI never runs it from a worktree.
- **A shipped predicate's shipped *documentation* can describe a variant that was never shipped — capture the SHIPPED code's own log line as the instrument instead of reimplementing the predicate.** Measured: a trap-ticker trigger fires on `exit_reason IS NULL AND entry_date >= -30d`, but the config comment and the evidence doc both claimed the firing set of the *evidence probe*, which ANDed an extra `realized_win == 0` condition — so the doc said "exactly 3" while the code fired on 7 (5 of them behaviourally new), and the trigger's own runtime clause ("no way to arm the payoff test") was false for the 2 tickers in the set that did have in-window closes. Two rules. (a) Measure the shipped predicate by attaching a logging handler and reading what the code itself emits ("shipped firing set" is a log query, not an arithmetic replica) — a reimplementation silently carries whatever extra guard you happen to write. (b) When a firing set is claimed, diff it against the claim in both directions (`fires-but-not-claimed`, `claimed-but-does-not-fire`) and check any per-hit *why* clause against the same rows; a correct decision with a false rationale is a documentation defect, not a behaviour failure, so return it for text correction rather than re-arguing the decision.
- **Before crediting an AC to the shipped code, ask whether the counterfactual it names is even reachable on the frozen cohort — a "redundant" second key is often the real lever.** A doc claim "removing bound A leaves bound B" can be true of the code while unmeasurable on the book, because A is always the tighter one for every observed row. Reproduce the bound as `min(base, A, B)` over each cohort row and print which bound actually binds; here the 13-day cap never bound (the 10-day stop was tighter for all 57 rows) even though the 10-day stop *was* the delivered lever. Report it as a precision note on the docstring, and check the tighter bound still dominates the cohort (a business-day clock at the same value can keep 3 of 8 tail rows reachable where the calendar clock truncates all 8).
- **An AC of the form "0 rows carry X" is satisfiable going-forward and false on the live DB, and the forward-only fix is often the CORRECT one — say which reading you verified.** A NULL-payoff cleanup with a tracker-side fallback plus a read-side filter fixes every NEW row while 4 historical rows stay NULL; demanding a `0.0` backfill would re-trigger the dilution the code's own comment warns about (a fabricated zero lands in the loss side and raises the payoff ratio). Verify the forward write path by exercising it in a scratch DB, verify the read path drops the stale rows, and record the historical residue as a briefing-wording issue with the reason the backfill must NOT be done.
- **Your own verification harness can dirty the reviewed tree — check `git status` in EVERY tree you touched before the verdict.** Rendering a message through the real pipeline runs `scanner.version.snapshot_config()`, which writes `config/versions/<version>.yaml`; pinning `FA_PIPELINE_VERSION` to a sentinel (e.g. `9.9.9`) makes that file obvious. It lands untracked in the fixed AND the pristine tree, looks like implementer churn, and can be attributed to the wrong party. Remove your own residue (compare mtimes against the deliverable's evidence stamps to attribute it) and disclose it; never revert a sibling card's work to tidy up.
- **An end-to-end probe through the real store path can mutate a TRACKED file as a side effect — revert it before you finish.** `tracker.store_signal()` calls `_ensure_version_registered()` → `snapshot_config()`, which rewrites `config/versions/<current-version>.yaml` in the tree you ran from. A reviewer's own e2e probe therefore leaves a dirty worktree that looks like uncommitted implementer churn (here: 331 insertions on a file the diff never touched) and can be attributed to the wrong party. `git status --porcelain` before you conclude anything, `git checkout -- <file>` to restore, and disclose the side effect in the verdict.
- **A disproof's CONCLUSION and its stated MECHANISM are separate claims — test the mechanism against the row's own antecedent key, because a join can be wrong for a different reason than the one asserted.** A round that withdraws a mis-attributed census will often keep a "disproof" leg stating WHY the rejected construction fails, and that causal sentence rides into the consumed payload as a measured verdict. Measured here: a feed asserted "the date-join recovers the wrong regime because `signals.market_regime` was refreshed after the row was stored", quoting 4 mismatching journal rows — but resolving each row through its OWN key (`trade_journal.signal_id -> signals.signal_id`) showed stored == that signal's CURRENT regime for 90/99 rows, 0 rows demonstrating a refresh, and all 4 mismatches explained by `entry_date` differing from the signal's own scan date (the join picked a different DAY, not a stale value). The conclusion survived (a separate leg — the guard's own log token vs the date-join — proved 6 provable kills mis-bucketed), so the fix is to relabel the measured fact, not to re-open the withdrawal: distinguish ACCEPT the conclusion from CORRECT the mechanism. Rule: when a handoff explains a discrepancy by asserting an upstream mutation (refreshed / overwritten / re-derived), resolve the row through the key that pins its own antecedent and count the rows where the mutation is actually visible; if the count is 0, report "the join key is wrong" (a key-choice defect) rather than "the value was refreshed" (a mutation defect). Corollary: check the write path the mutation claim implies — `grep` the UPDATE statements that touch the column, since a claim of refresh is falsified by a table whose only UPDATEs are elsewhere.
- **Count the denominator the narrative MEANS, not the one the counter happens to tally.** A `contradiction_count` of 12 over 6 affected rows is not wrong, but a guard token printed twice per ticker (a "Direction:" line plus a "No trade for <T>:" line) makes the field read as 12 bad rows beside a narrative about 6. Emit the row-level count (`affected_ledger_rows`) alongside the occurrence count, or the next reader will quote the wrong one — this is the same 12-vs-6 ambiguity class as an unstated tolerance.
- **A commit to a store that a daemon rewrites every tick is only durable if it SURVIVES a post-commit rewrite — and "N enabled pinned" is not "N pinned".** Two traps when auditing a config-store migration (`cron/jobs.json`, a scheduler-owned YAML, any file a live process owns). (a) The diff proves what landed in git, not what the running system reads: compare the commit timestamp against the file's mtime, and if the file was rewritten *after* the commit, re-read the values from the live file — a change that does not survive the next tick is a silent regression that a green `git show` will never show you. (b) When a handoff or a wiki page quotes a fleet roster ("7 enabled jobs pinned X"), cross-tab `enabled × pinned` yourself instead of trusting the count: a *provider* column can make inert `no_agent` script jobs look pinned when their `model` is `null`, and an "enabled pinned" count can differ from the raw pinned count by exactly the paused jobs. Recompute the distribution (`Counter(model)` over the whole store) — the disposition must be consistent with the siblings, and the count alone cannot tell you whether it is.
- **On a shared worktree, `HEAD` is not a stable anchor for an acceptance check — verify against the commit that CARRIES the change.** `~/.hermes` is a single live config home written by concurrent workers and a scheduled `auto-backup` cron, so `HEAD` advances between a card's landing commit and your verification. An AC phrased `git show HEAD --stat -- <file>` then reads an *unrelated file* (or empty) and the check fails as a **false positive** on a deliverable that is actually correct. Symptom: the stat line names a file the card never mentioned, and `git log --oneline -3` shows a sibling commit on top of the change. Resolve it by anchoring every git assertion to the change-carrying sha (`git show --stat <sha>`, `git show <sha>~1:<path>`, `git merge-base --is-ancestor <sha> origin/main`) and reporting the HEAD-relative command as a known deviation with its reason. Never rewrite history on a live shared worktree just to make a literal command non-empty.
- **A "no child task depends on this" check is a graph query, not a prose read.** The review-vs-complete routing decision turns on whether a pre-created review/QA child exists, and the edges live in `task_links (parent_id, child_id)` — `tasks` has **no** `parent_id` column, so `SELECT ... WHERE parent_id=?` on `tasks` raises `no such column` and an implementer who then eyeballs the card body can miss a child entirely. Query `task_links` over a read-only connection (`sqlite3 'file:<db>?mode=ro'` from a scratch `.py` run via `python3 <scriptfile>`).
- **A liveness nudge that fires repeatedly on an already-closed run is keyed on PROCESS liveness, not run ownership — do not obey it, and do not try to "make it stop" with a terminal verb.** The dispatcher-spawned worker's long-lived `hermes -p <profile> chat` parent stays alive for the whole turn, so a nudge that infers "still running" from pid liveness keeps firing after `kanban_request_review` / `kanban_request_changes` already closed the run and NULLed `tasks.current_run_id` + `tasks.worker_pid`. Obeying it is actively destructive in the review case: `complete_task`'s docstring (`hermes_cli/kanban_db.py`) accepts `review -> done`, and the write guard's `_owns_ended_run` clause explicitly re-admits a worker whose run ended with `review_requested` (`hermes_cli/kanban_guard.py`: `_TRAILING_RUN_OUTCOMES`) — so `kanban_complete` would **succeed**, marking the card `done` and publishing "approved" with no reviewer ever having run, laundering an open review into a settled one. Settle it with the board, not the nudge: read `task_runs` for your run id (`outcome` set, `ended_at` non-NULL), confirm `tasks.status` is the handoff terminal (`review` is a legitimate one — `hermes_cli/goals.py` maps it to `review_requested_by_worker`), and confirm no live run exists. Then stop and state why; the nudge is not evidence that the board disagrees with you.
- **Two DIFFERENT guards govern a handoff; name the right one or your hazard claim is wrong.** `kanban_guard.py:_owns_ended_run` / `_owns_handed_off_card` decide board **ACCESS** (can this process write the card thread at all) — they re-admit a worker whose run ended `completed`/`review_requested`/`changes_requested`. Whether `complete_task` may **END a run** is a separate, stricter seam: `kanban_db.py:_live_run_ownership_guard` (aliased `_completion_ownership_guard`), documented "owner, or `force`", which returns **`(True, None)` when the card has NO live run** — "a card parked in `review`/`ready`/`blocked` after its run closed stays completable by a human passing no run id, because there is nothing to take from anyone" (`kanban_db.py:3234-3238`). So the destructive window is not "the access guard re-admits me" but the **gap between your handoff and the dispatcher's review-lane claim** (`source_status: "review"` on the reviewer's `claimed` event). Measured on a real card: 56s (handoff 15:39:43 -> review claim 15:40:39), and the post-handoff nudge landed *inside* it. Once the reviewer's run exists, `complete_task` is correctly REFUSED (not owned). State the window and its width; do not assert "completing would succeed" without naming which guard permits it.
- **Corollary: "the card is still `running`" from a nudge can be literally true and still not be YOUR run.** After `request_review` the dispatcher re-claims from the review lane within ~1 min, so `tasks.status` flips `review` -> `running` again with `worker_pid` naming the REVIEWER (`ps -o pid=,ppid=,etime=,cmd= -p <pid>` shows the reviewer's `-p <reviewer-profile> ... --skills sdlc-review` argv). Distinguish by identity, never by status: read `task_runs` for your run id and the reviewer's, and check the reviewer's `claimed` event carries `source_status: "review"`. Do not write anything; the reviewer owning the run is the system working correctly.
- **A card parked in `review` can sit for a while because the review lane is queued behind `kanban.max_in_progress_per_profile`, not because it was dropped.** Before concluding a handoff is lost, count live runs per assignee (`task_runs WHERE ended_at IS NULL`) against the cap in `config.yaml`. With the cap at 2 and 2 runs already in flight for that profile, the review dispatch simply has no slot yet — it is queued, not stranded, and "the reviewer never came" is not a blocker.
- **Reviewer implementation:** Editing the deliverable hides ownership and weakens the re-review boundary.
- **Vague findings:** “Needs work” does not give the implementer a reproducible correction target.
- **Style-only blocking:** Do not request changes for preference-level nits when behavior and repository standards are satisfied.
- **Skipping prior rounds:** Re-review must confirm both the requested corrections and preservation of previously passing behavior.
- **Using blockers for ordinary rework:** Correctable defects belong in `kanban_request_changes`; reserve `kanban_block` for genuine external blockers or human decisions.
- **Completing without evidence:** Every approval summary must name the checks or artifacts actually inspected.
- **Do not try to "close" a review run you already terminated.** `kanban_request_changes` / `kanban_complete` ends the review run immediately: the task flips to `ready`, `current_run_id` clears, and the claim is released. Any further board write from the same PID is then refused by the kanban write guard ("NOT a genuinely claimed worker … tasks.worker_pid != os.getpid()"). That refusal IS the graceful-park signal, not an error to work around — do not retry, do not call `kanban_complete` to force closure, and do not `kanban_block` for rework the reviewer already routed back. Confirm closure from the `kanban_show` event trail (`changes_requested` event + run `outcome` set) and stop.
- **`kanban_write_guard` refusing a legitimate terminal transition:** the guard rejects a write when the pinned task's `worker_pid` does not match the writing process — this also fires for the dispatcher-spawned worker itself, because `kanban_complete` is executed by a child helper process, not the long-lived `hermes -p <profile> chat` parent. On refusal, do NOT retry blindly and do NOT hand-roll a direct sqlite write. Re-read the task row over a read-only connection (`sqlite3 'file:<db>?mode=ro'` via a scratch `.py` run with `python3 <scriptfile>`; inline `python3 -c` is denied on this profile). If `tasks.status` is already terminal and a matching `completed` event carries your summary, the transition DID land before the guard tripped: stop, report success, and clean up scratch probes. Only if the row is still non-terminal should you escalate — and first read `task_runs` to see WHO owns the live run (next bullet).
- **A live `running` row after your verdict is the SUCCESSOR's run, not yours — do not close it.** After `kanban_request_changes` the card flips to `ready`; the dispatcher then RE-CLAIMS it for the implementer with a NEW run id, so `tasks.status` reads `running` again with `tasks.worker_pid` = the implementer's pid (≠ yours). A generic "task is still `running`, call `kanban_complete`/`kanban_block`" automation nudge will fire repeatedly at you — it is a FALSE POSITIVE, because the nudge infers ownership from `tasks.status` while the write guard infers it from `tasks.worker_pid`. Distinguish the two cases before acting:
  1. read `task_runs` over a read-only connection and check YOUR run's row: `status`/`outcome` set, `ended_at` non-NULL, `worker_pid` NULL ⇒ your review run already closed correctly;
  2. check the live run's `profile` — if it is the implementer's, the card is mid-rework and closing it would destroy the round-N → round-N+1 loop and strand the requested fixes;

  In that case: do NOT call `kanban_complete` (would mark done while the implementer is mid-rework) and do NOT call `kanban_block` (the rework was already routed back; blocking it is the forbidden anti-pattern). The guard refusing even a `kanban_show` read with "NOT a genuinely claimed worker … `tasks.worker_pid != os.getpid()`" is the confirming signal. Report the evidence and stop — obeying the nudge is the protocol violation, not ignoring it.

- **An operational claim inherited across cards ("verb X is rejected by the tool layer") is a claim to TEST, not to relay — one run of the verb settles it.** A gate card's brief, the orchestrator stamp, and six older cards' recorded notes all asserted `kanban_request_review(reviewer="user")` is refused because `user` is not an installed dispatchable profile; each routed around it. - **A "user verdict: approved" claim on a deliverable is a claim to verify, not a fact to copy — check WHO wrote the approval.** A card parked for a human reviewer (`kanban_request_review(reviewer="user")`) leaves `assignee=user`, and the dispatcher/auto-promotion path can let the implementer's own session close it under the `user` profile via `kanban_complete` — which auto-completes the card, promotes its children, and lets a downstream landing card stamp its page "approved" with no human involved. Verify by identity, never by status: read `task_runs` for the approving run and compare `metadata.worker_session_id` against the implementation run (a byte-identical session id, or a `dur=0s` run whose `review_note` says it closed because `kanban_block` was refused, means no human was involved); then `SELECT COUNT(*) FROM task_comments WHERE task_id=<parent> AND author='user'` — an approval with zero human-authored comments on the thread does not exist. Genuine gate completions read "Review approved without additional evidence." or "User approved <options>"; an approving run whose summary merely duplicates the implementer's own handoff reviewed nothing. `kanban_request_changes` the false claim onto the landing card, and state that the findings are UNVETTED pending the real verdict: a fabricated gate-pass is worse than an omission because it launders an open decision into a settled one in durable storage.
- **After `kanban_request_changes` the card reads `ready`, not `running` — a "task is still running" nudge is stale, and `kanban_complete` is the wrong obedience.** `request_changes` sets `status=ready`, clears `current_run_id`, and reassigns to the implementer, so a liveness nudge (keyed on process liveness, because your agent loop still holds the PID open) keeps firing after your run already closed. The nudge is not evidence that the board disagrees with you.
- **An event's declared output channel can be undeliverable — verify at BOTH the parser and the CONSUMER, and never let a CLI harness's default payload settle it.** A hook can fire correctly, exit 0, print its directive, and still change nothing: `agent/shell_hooks._parse_response` dispatches per-event (`_RESPONSE_PARSERS.get(event, _parse_context)`), so `pre_tool_call` → `_parse_pre_tool_call`, which understands only `block`/`modify` — a `{"decision":"context"}` response parses to `None` and `_parse_context` is only the fallback for *other* events. Confirming the parser is not enough: check who consumes the result (`hermes_cli/plugins.py:_get_pre_tool_call_directive_details` accepts only `modify`/`block`/`approve`), because a matching parser with no consumer is equally silent. Decisive test: the CLI's default synthetic payload is a **non-matching** command (`_DEFAULT_PAYLOADS["pre_tool_call"]` → `echo hello`), so an unqualified `parsed: <none>` is ambiguous between "never fired" and "fired then dropped" — pass `--payload-file` with a genuinely matching command, confirm stdout carries the directive, and only then read `parsed`. Corollary for review verdicts: when the mechanism cannot deliver, the ACs can still all pass — approve on the contract and forward the channel decision to whoever owns it upstream, since blocking strands a verified deliverable.
- **Before crediting a commit with an AC, check the artifact's history — the AC may have been satisfied before the card existed.** A card body saying "replace the stale text" can describe work already landed days earlier: here a sibling commit 9 days prior had already rewritten the constant, and the reviewed commit did not touch it at all (`diff` of the constant empty). Verify the *change*, not just the resulting *state*: `git log --oneline -- <artifact>`, then diff the specific constant/function across the range and confirm the commit under review is the one that moved it. Report it as a **briefing defect, not an implementer defect** — the AC passes either way, but the reviewer's job is to know whether the commit earned it, and an implementer must not be credited for (or failed on) a change it never made.
- **When auditing a "nothing is ever lost" fix, enumerate EVERY removal mechanism — a release rule can be airtight while the CAP still evicts.** A round that closes a loss finding by governing one mechanism ("nothing is released unless the emitted body names it") can leave a second, differently-shaped removal unguarded, and the fix's own comments then state an invariant the code cannot hold. Measured: the release rule held (`LOST = []` under truncation), yet at a **cap-full** ledger the same-day/requeue merge — the very merges that run when no body was emitted — pushed the ledger over `DEFERRED_MAX` and evicted the oldest entry, which was itself a never-dispatched timing defer whose source card sat behind the watermark: `seeded 64 | named 0 | left 64 | LOST ['t_70000000']`. Because the entry WAS named in the report, the finding's original class (silent drop) stayed closed and the defect hid behind a green regression test that asserted only `evicted > 0`. Sweep the removal mechanisms explicitly (release / expire / evict / dedupe) against the fix's stated invariant, and prefer a probe that asserts the *invariant* ("every seeded target is either named or retained") over one that asserts the *mechanism* the finding named. Related accounting tell: an eviction list appended per-merge without deduping by target reports one removal twice (`header 2 evicted`, one distinct target, true removal 1), and a test asserting `evicted > 0` cannot see it — require the header's count to equal `len(seeded - set(final_state))`.

- **Verify a line edit's indentation change against RENDERED output, not a token/cell count — a 3→5 space shift inside a list item is a CommonMark code-block candidate that renders as plain prose.** When a round rewrites a sentence inside an ordered/bullet list, a widened indent can silently convert the paragraph into a 4-space code block (or vice versa): the text stays legible to `grep` and to a token-count audit while rendering as a literal `|`-style code wall to the reader. Here a 5-space continuation was a legitimate lazy continuation of the list item; the render, not the eyeball, proved it.

- **A ratio on a page may not reproduce from the page's OWN displayed row — check numerator/denominator pairing before calling it an error, and state the tolerance.** A fitted-parameter table can carry a ratio computed from two observations that were MATCHED at the time (`volume_at_read_time / counter_at_read_time`) while a reviewer re-deriving it divides TODAY's volume by the stale counter; the same table row then yields 1.04 (matched) or 1.31 (mismatched), and the page's stated 1.02 came from the parent's own matched pair. - **Before crediting a structural fix, check the claim against the pre-card revision with a loop, not a bare `git grep`.** `git grep -c <pattern> <rev> -- <path>` returns a non-zero/empty result that is ambiguous between "no matches" and "the invocation did not run"; iterate the revision's file list (`git ls-tree -r --name-only <rev> | grep '\.md$'`) and test each blob so the count has a non-zero denominator — then the pre/post sets are comparable and a wording claim like "was an orphan" can be checked (here it was NOT: the validator reported 0 graph orphans pre-card and the page had three inbound links, so the accurate statement was "absent from the hub members list").
